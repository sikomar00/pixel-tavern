# 최신 커밋 리뷰

작성일 2026-11-05. 대상: `main`의 `271ff83`(= `origin/main`) + 커밋 전 수정.
표기: **[시험]** 가짜 엔진의 자동 시험 · **[실측]** 실제 Windows에서 직접 돌려 잼 · **[미검증]** 확인하지 못함

## 1. 범위와 방법

- 저장소 상태: `git status`, `git log`, `git show --stat HEAD`, `git ls-files`(45개 파일)로 확인. 시작할 때 작업 트리는 깨끗했다.
- 읽은 것: `hooks/` 18개 파일(약 2,140줄, 생성된 그림 `art/` 제외), `tests/` 7개 파일(약 1,530줄), `tools/`, `types/`, README.
- 실행한 것: `claude plugin test`(74개 통과), `claude plugin validate`(통과), 코드 리뷰(낮은 강도), 실제 Windows 실험(`tools/player_check.py`).
- 받은 분석 요청의 전제가 **오래된 저장소 상태**였다. 시험이 루트의 한 파일이라고 했지만 실제는 `tests/`의 6개 시험 파일 + 공용 `kit.tsx`이고, 도움말 영역도 6곳이 아니라 5곳이다. 이 문서는 실제 상태를 기준으로 했다.

## 3. 구조 평가

- 계층: 데이터(`scenes`, `volume`, `format`) → 상태(`state`) → 바깥 세계 어댑터(`git`, `radio`) → 동작(`actions`, `alerts`) → 화면(`banner`, `panel`, `music`, `layout`, `usage` …) → 연결(`register`). 바깥 세계는 파일 하나씩에 모여 있다. 자세한 것은 `docs/architecture.md`.
- 크기 규칙: 모든 파일이 최대 500줄 안. 권장(300줄)을 넘은 것은 `panel.tsx` 349줄, `state.ts` 314줄 두 개(R-16).
- 함수 길이·중첩·복잡도는 도구로 재지 않았다 **[미측정]**.
- 실행 시점 순환 의존 없음(타입만 서로 가리키는 곳 둘).

## 4. 찾은 문제와 조치

시험이 통과한다고 위험이 없는 것은 아니었다. 시험이 보지 않는 "실제 환경" 쪽에서 5건을 찾아 고쳤다(자세한 것은 `remaining-issues.md`의 F-01~F-05).

| ID | 문제 | 조치 |
|---|---|---|
| F-01 | `git status`가 사용자의 `git add·commit`을 막을 수 있고, 저장소 설정의 `fsmonitor` 명령을 실행할 수 있음 | `--no-optional-locks`, `core.fsmonitor=false` |
| F-02 | 방송 서버가 죽으면 끝없이 재연결 | 5번 뒤 포기·알림 |
| F-03 | 앱이 강제 종료되면 소리만 나는 재생기가 남을 수 있음 | 부모 프로세스 감시 |
| F-04 | 파일 이름에 제어 문자가 있으면 **패널 전체가 사라짐**(엔진이 거부) | 기록할 때 제거 |
| F-05 | 부모 PID를 못 읽으면 감시 코드가 재생기를 5초 만에 죽임(코드 리뷰 지적) | PID가 없으면 감시 안 함 |

F-04는 시험을 먼저 써서 발견했다. 처음에는 클릭할 때의 경로만 고치려 했는데, 시험이 "패널을 그릴 때" 이미 실패해서 고칠 자리를 기록 시점으로 옮겼다.

## 5. 실제 Windows 실험(소리 없음)

환경: Windows 11 Pro(10.0.26200), Windows PowerShell의 `MediaPlayer`. 음량 0. 방송은 REYFM 로파이(정상), `127.0.0.1:9`(죽은 주소). 재현: `python tools/player_check.py normal|dead|orphan`.

| 실험 | 결과 | 고치기 전 |
|---|---|---|
| 정상 방송: 시작 → 재생 신호 | **5.0초**(이전 실행 5.4~6.5초) | 같음 |
| 정상 방송: 자원 | 14초 2.3초 CPU → 24초 3.2초 CPU(10초에 약 0.9초 ≈ 한 코어의 9%), **메모리 137 MB**(이전 131~135 MB) | 같음 |
| 끈 뒤 남은 재생기 | **0개** | 같음 |
| 죽은 주소 | 재연결 시도 2·17·33·48·64초 → **79초에 포기, 종료 코드 0** | 15.5초마다 끝없이 |
| 부모를 강제로 죽임 | 재생기 **4.3초 만에 모두 끝남**(이전 실행 3.2~3.5초) | 고아로 남음(12초 뒤에도 살아 있음) |
| `git status` 속도(45개 파일 저장소, 5번) | 옵션 없음 62~209 ms(중앙값 85) / 안전 옵션 74~143 ms(중앙값 89) → **차이 없음** | — |

측정 방법의 주의: 처음 실험은 재생기를 세는 조회 명령이 자기 자신을 세어 "2개"로 나왔다(재생기 1 + 조회 1). 재생기 둘이 뜬 것이 아니었다. `player_check.py`는 패턴을 `radi[o]`로 써서 자기 자신을 세지 않게 고쳤고, 같은 실험에서 "죽이기 전 1개"로 바르게 나온다.

그 밖에 알게 된 것: 파이프가 끊겨도 .NET의 `Console.Out.WriteLine`은 오류를 내지 않아서 "출력이 끊기면 스스로 끝난다"는 처음 방식은 동작하지 않았다(실험으로 확인). 그래서 부모 프로세스 감시로 바꿨다.

## 8. 결론

기존 기능은 그대로 두었고(기존 70개 시험 변경 없이 통과) 시험 4개를 더했다(74개). 시험이 못 보던 실제 위험 5건을 고쳤고, 그중 프로세스 쪽 3건은 실제 Windows에서 효과를 확인했다. 아직 확인하지 못한 것(실제 앱에서의 표시·두 채팅 공유·강제 종료)은 `remaining-issues.md`의 R-03~R-05와 `docs/test-plan.md`의 사람 확인 목록에 있다.
